# SquadMC 2.1.5-perf.1 — загрузка чанков снарядами и оптимизация

База: `4a57d614a86101772ec9b6303546a41f61be878b` (ветка main).
Цель: Forge 1.20.1, Java 17, Superb Warfare **0.8.9.2**.

## Что изменено

- Все сущности, наследующие Minecraft `Projectile`, из пространств имён
  `superbwarfare` и `squadmc` используют общий загрузчик: пули, снаряды,
  ракеты и собственные снаряды мода. Код снарядов TACZ и других модов
  этот загрузчик не перехватывает.
- Проверяется весь отрезок движения за тик, включая промежуточные чанки
  быстрых снарядов и соседний пояс чанков для столкновений. Есть загрузка
  вперёд ещё на один шаг; её готовность не задерживает уже безопасный шаг.
- Заявки объединяются по измерению и координатам чанка. Лимиты общие для
  всего сервера, а не отдельные для каждой пули или измерения.
- Загрузка запускается временными region tickets без синхронных `getChunk`
  и ожидания futures в новом загрузчике. Minecraft сам обрабатывает загрузку
  и, при необходимости, генерацию. Чанки игроков и `/forceload` не отключаются.
- Собственный загрузчик FastThrowableProjectile в SBW и его обход обычного
  тика отключены, пока включена новая система. При отключении возвращается
  исходное поведение SBW. Старые сохранённые заявки SBW могут дожить до своего TTL.
- Обломки передают начало отсчёта возраста вместо изменяющегося возраста
  каждый тик. Поздний вход игрока и NBT `Age` поддерживаются; при загрузке
  сохранённого обломка отсчёт восстанавливается с сохранённого возраста.
- Поиск уничтоженной техники работает по набору техники SquadMC, обновляемому
  событиями входа/выхода, вместо обхода всех сущностей мира каждый тик.
- Рендер обломков повторно использует временные векторы вместо их выделения
  на каждый quad. Кеш моделей принадлежит экземпляру рендера и сбрасывается
  при пересоздании рендереров во время перезагрузки ресурсов.

Количество частиц, модели, геометрия коллизий обломков, текстуры, звуки,
дальность эффектов и настройки дымового рендера не урезаны.

## Настройки и поведение при перегрузке

Файл после запуска: `<мир>/serverconfig/squadmc-performance-server.toml`.
Для новых миров можно положить шаблон в `defaultconfigs/`.

```toml
[projectileChunks]
enabled = true
maxTickets = 64
startsPerTick = 2
retainTicks = 40
maxWaitTicks = 200
pathLimit = 128
```

Это консервативная отправная точка для 30–50 игроков, 8 ядер Ryzen 9 и 16 ГБ памяти, а не
измеренная гарантия производительности. `maxTickets` — число центров tickets:
Minecraft дополнительно загружает соседей, поэтому это **не** предел общего
числа загруженных чанков. Очередь вместе с активными заявками ограничена
`maxTickets * 2`. Повторные заявки не занимают новые места.

Снаряд ждёт перед шагом, если необходимые чанки ещё не готовы к тикам
сущностей. Его полный серверный тик в этот момент пропускается: не происходит
частичного продвижения физики/взрывателя. Это меняет время полёта при ожидании;
клиент может временно показывать предсказанное положение. Через 200 тиков
непрерывного ожидания снаряд удаляется без серверного взрыва, с ограниченным
по частоте предупреждением в журнале. Слишком длинная или некорректная
траектория также ждёт и завершается по тайм-ауту. Это явная защита от перегрузки,
а не гарантия доставки каждого выстрела при произвольной нагрузке.

Заявка снимается через 40 тиков без использования. Во время пролёта её
продлевают все нуждающиеся в ней снаряды. При выгрузке измерения и остановке
сервера состояние очищается; постоянные записи `/forceload` не создаются.

Для боя лучше заранее сгенерировать карту: ограничение количества запросов
не отменяет стоимость генерации новых территорий, крупных взрывов и чужого
кода, который сам синхронно запрашивает чанки. При тайм-аутах сначала смотрите
MSPT и журнал, затем меняйте лимиты; повышение лимитов увеличивает нагрузку.
После изменения настроек перезапустите сервер.

## Установка и совместимость

Нужен одинаковый новый JAR **на сервере и у игроков**. Сетевой протокол поднят
с 1 до 2: старые клиенты отклоняются при подключении из-за изменения формата
синхронизации обломков. Сохранения используют прежний NBT `Age`.
Проверять сначала на копии мира с реальными конфигами сборки.

Исходники применяются к указанной базе командой `git apply squadmc-performance.patch`.
Для обычной сборки нужны исходные локальные зависимости в `libs/`:
`superbwarfare-0.8.9.2.jar`, `tacz-1.20.1-1.1.8-hotfix2.jar`, `aas-beta-1.8.0.jar`.
Команда: `bash gradlew build` (или Gradle через IDE на Windows).

## Проверки

Независимые тесты очереди и траекторий запускаются без Minecraft и mod JAR:

```sh
mkdir -p build/performance-tests
javac -d build/performance-tests \
  src/main/java/tech/squadmc/squadmcor/performance/ChunkLeaseBudget.java \
  src/main/java/tech/squadmc/squadmcor/performance/ProjectileChunkPath.java \
  src/test/java/tech/squadmc/squadmcor/performance/PerformanceRegressionTest.java
java -cp build/performance-tests tech.squadmc.squadmcor.performance.PerformanceRegressionTest
```

Проверяются быстрые диагональные траектории и отрицательные координаты,
ограничение длины, 10 000 заявок на один чанк, общий лимит, FIFO, освобождение
после последнего пользователя и раздельная очистка измерений.

Интеграционные GameTest-проверки: `bash gradlew runGameTestServer -I src/gametest/enable.gradle`.
Они проверяют перехват полного тика пули, снаряда, ракеты и ПТУР в незагруженной
области, а также загрузку чанков и возобновление движения пули. Требуются
обычные зависимости проекта. Эти тесты не включаются в нормальную сборку JAR.
Проверка завершения генерации временно увеличивает ожидание до 1200 тиков:
она проверяет асинхронное завершение независимо от защитного тайм-аута в
рабочей конфигурации, затем восстанавливает настройку.

В среде проверки пройдены компиляция Java 17, самостоятельные тесты очереди
и траекторий (2 255 532 проверки), а также оба GameTest на Forge 47.2.0 с
официальными SBW 0.8.9.2 и TACZ 1.1.8-hotfix2. Локальный `aas-beta-1.8.0.jar`
отсутствовал: только для проверки эту зависимость исключали временным Gradle
init script. Основной `build.gradle` не изменён. Проверка совместимости с
реальным AAS, клиентского визуала и боя на 30–50 игроков остаётся необходимой.

Для приёмки на сервере: стрельба за simulation-distance по мишеням в уже
сгенерированных и новых чанках; несколько залпов одновременно; уход стрелка
из области; переход между измерениями; окончание полёта и освобождение
заявок; перезапуск мира; поздний вход наблюдателя к горящему обломку.
На клиенте сравнить огонь/дым и перезагрузку ресурсов F3+T.
Измерять MSPT p50/p95/p99, паузы GC, память, число загруженных чанков и FPS
в одинаковых сценах до/после. Процент ускорения без этих замеров не заявляется.
